## Decisions
- **Fibroblast ECM deposition must be nonzero.** In fibrotic lung and kidney only a minority of
  collagen-producing cells are αSMA⁺, and αSMA⁻ collagen producers activate TGF-β equally well
  (Sun et al., 2016). In corneal keratocyte lineage fibroblasts deposited *more* fibrillar collagen
  I/V, myofibroblasts more fibronectin (Acosta et al., 2023). Myofibroblast rate stays higher;
  fibroblast rate is no longer zero.
- **Myofibroblast GF secretion stays low in v1, but relabelled as a compensation rather than
  biology.** Biologically it should be high (Wilson, 2020; Popova et al., 2010), but the autocrine
  loop is gated by matrix stiffness — contraction activates latent TGF-β only against a resisting
  matrix (Wipff et al., 2007). v1 has one lumped active field and no stiffness, so the brake is
  missing and a high rate would run away. Raise it in v2 with the latent/active split.
- **The αSMA binary is a modeling convenience with contested footing** (Sun et al., 2016) — carried
  as a standing caveat, not a reason to change v1.

## Session 2: CC3D field-slicing crash, and fixing the `cc3d` env

**Focus:** While implementing Group 1 of `model/cc3d/subepithelial_fibrosis_draft/`, a field
read pattern from the cc3d-expert skill (`np.array(self.field.G[:, :, 0])`) was crashing the
C++ backend with no Python traceback. Isolated the cause, fixed the skill guidance, and fixed
the broken `cc3d` conda env on this machine.

### Did
- Wrote a minimal standalone repro (`field_crash_repro/`, one `DiffusionSolverFE` field, a
  steppable doing nothing but the slice in `step()`) and confirmed the crash outside the draft
  model, ruling out anything specific to that project's XML/steppables.
- Bisected the actual trigger. It is **not** the numpy call — `field[:, :, 0]` alone (a plain
  slice, no `np.array()` wrapper) crashes the same way, and even a bounded slice
  (`field[0:5, 0:5, 0]`) crashes. Only integer indices (`field[x, y, 0]`) are safe. This is a
  stronger/different finding than the numpy-specific theory in the task description.
- Confirmed the raw Windows exit code directly (bypassing `conda run`'s wrapper, which reports
  a misleading 127): `-1073740791` = `0xC0000409` = `STATUS_STACK_BUFFER_OVERRUN`.
- Built a throwaway `cc3d_410_probe` env (compucell3d 4.10.0, the newest available on the
  `compucell3d` conda channel) and ran the identical repro: **same crash, same exit code.** Not
  specific to 4.9.0 — reproduces on the latest packaged CC3D too. Removed the probe env after
  testing (not kept).
- Searched CC3D's GitHub issues and numpy's issue tracker for a known match; found nothing
  specific. Treating this as an unreported bug in the Windows conda-forge build's field
  `__getitem__` binding, not (yet) a known/tracked issue upstream.
- Updated `.claude/skills/cc3d-expert/references/steppable-patterns.md` (Fields section) and
  `references/debugging-and-errors.md` (Segfaults list + diagnostic recipe) to warn against any
  `:`-slice on a field object and to show the integer-index loop as the only recommended
  pattern. (Note: `.claude/` is untracked in this repo — these edits live only in the working
  tree, not in git history.)
- Diagnosed the broken `cc3d` env: `conda env list` showed it present but `conda list -n cc3d`
  showed only a bare Python 3.14.6 — no `cc3d` package at all, and CC3D's packaged builds only
  target Python 3.12. The `mamba install compucell3d=4.10.0` step from `model/cc3d/README.md`
  must have failed silently (no build for py314) and been abandoned mid-setup, while the
  already-working `cc3d_490` (CC3D 4.9.0, Python 3.12.2) was created instead and never
  reconciled with the docs.
- Per your call: deleted the broken/empty `cc3d` env on this machine and updated `CLAUDE.md`
  and `model/cc3d/README.md` to stop hardcoding a single env name — the CC3D env is `cc3d` on
  one machine and `cc3d_490` on the other, so the docs now say to check `conda env list` +
  `python -c "import cc3d; print(cc3d.__version__)"` per machine rather than assuming.

### Results / observations
- Crash is reproducible, minimal, and confirmed platform-general across two CC3D versions on
  Windows conda-forge builds (4.9.0 and 4.10.0). Not tested on Linux/Mac — no access here.
- The task description's framing ("numpy slice conversion crashes... per-pixel loop works")
  undersold the bug slightly: it's not numpy-specific, it's slicing-specific. Worth knowing if
  this comes up again — `np.array(field[x, y, 0])` (numpy wrapping a single scalar element,
  no slice) would presumably be fine, since the crash is in the field's own `__getitem__` for
  slice objects, not in numpy's array conversion machinery.
